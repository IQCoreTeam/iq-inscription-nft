# Derived outfit view — local integration candidate

This is a read-only adapter for the existing gateway/router. It does not replace immutable `/token-meta/{M}`, `/img/{C}` or `/data/{signature}` responses. An opted-in NFT points at `/wardrobe/metadata/{asset}`; the original IQ M signature remains in its Core Attributes and derived metadata.

Supply the host's already-budgeted Core reader, `createWardrobeReader` from the portable client, existing IQ metadata reader, and collection renderer. The Core reader must return the verified Core asset, including collection authority and Attributes. The metadata reader returns the exact original IQ bytes, never arbitrary HTTP metadata selected by an NFT owner. The renderer consumes the committed loadout and the collection's pinned layer recipes.

`createOutfitView(...).handle(request)` accepts GET/HEAD for `/wardrobe/metadata/{asset}` and `/wardrobe/image/{asset}?r={revision}&h={loadoutHash}`. Apply the gateway's normal concurrency/rate limits outside this handler. Errors do not expose RPC credentials or filesystem paths. Unknown paths and methods fail; stale revision/hash image requests return 409 and must refresh metadata. Responses revalidate; immutable base metadata is separately cached by its signature with bounded entries and coalesced reads.

The original name/URI must still match the binding in the program-owned loadout. Current Core collection membership, metadata signature shape and original name are checked. Returned metadata does not mutate the cached original object. Existing on-chain recovery can restore the original URI; doing so intentionally makes the bound outfit view reject until an approved re-opt-in restores its bound identity.

Confirmed equip/remove/transfer actions should invalidate the affected avatar in the shared reader. Unobserved external changes become visible after its short cache interval; no polling or table `/notify` calls are needed. Marketplace cache refresh is venue-specific and not guaranteed by HTTP invalidation. Buying clients still include the on-chain outfit assertion to prevent races.

`npm test` exercises immutable-reference preservation, cold/repeated metadata reads, stale image rejection, method/path/address bounds and safe transient errors. The sibling Surfpool test wires this adapter to real Core/IQ accounts and the existing private Nubbies renderer, including a fresh-view cache-loss recovery check. Actual layer/art publication and production hosting remain separately approved actions.

## Public page state

`createPackPageStateReader` builds the production `/packs/{collection}/state` payload from the pinned V5 pool/epochs, pool-filtered issuance PDAs and the host's existing batched Core reader. It has no generated actors or fixture signer. Pass existing gateway metadata reads through `readMetadata(uri)`; metadata bytes must match each sealed definition hash before images, supply or creator tiers are exposed. `getAvatar(owner)` selects an existing indexed collection NFT; it must not scan all wallets. `readCoreAssets(addresses,{minContextSlot})` returns a Map of decoded Core assets or null only after validating raw Core owner/burn/absent state.

Reads share a one-second/coalesced snapshot, immutable metadata hashes and bounded per-owner avatar reads. There is no timer. Issuance queries include the exact pool memcmp at byte8, not a program/org-wide scan. This initial direct reader supports at most64epochs,64pack records and256traits; it rejects larger histories with an explicit indexed-reader requirement rather than truncating and pretending the result is complete. Production-scale indexed pagination is a separate host integration gate, not a claim made by this bounded reader. Mutable ownership/equipment stays verified against the chain.

The payload contains no test actors, private checkpoints, operator keys, source layers or unbounded transaction-history scan. A settled pack is returned only with four exact matching claim/issuance accounts. Equipped trait custody and the selected NFT's collection/owner/loadout/base identity are checked. Host writes should call `invalidate(owner?)`; ordinary reads reuse the bounded caches.

After a confirmed purchase, outfit change or metadata restore, the page may pass its signature as `after` to the state endpoint. The reader verifies a successful confirmed transaction on the configured chain and a relevant instruction for this exact pack pool, or an explicitly configured IQ program/collection opt-in/restore instruction. Only then does it invalidate the warm snapshot, once per bounded recent receipt entry. Its confirmed slot becomes a minimum-context floor through the mutable pool/epoch/issuance/Core/loadout reads. Repeated proofs coalesce and reuse verification; normal warm reads add no receipt RPC. Invalid, failed or unrelated signatures cannot flush the cache. The HTTP host applies its existing per-IP limiter to receipt proofs so this is not an unrestricted transaction scanner or timestamp cache-buster.
