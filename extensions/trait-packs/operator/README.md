# Pack epoch operator and recovery

This module runs only for explicitly configured markets in the existing backend. It does not create another public service, discover arbitrary collections, generate rewards or hold buyer keys.

`createPackOperatorMarket({connection,program,collection,signer,expectedGenesis,vrf,requestFundingLamports})` binds a configured V5 program/collection and the existing operator signer/ORAO SDK instance. Confirmed reads verify program ownership and pool/epoch identity, then compare the pool's provider treasury with live ORAO network configuration. The reviewed request-funding budget must cover the live SOL request fee. Provider V2 seed/client identity is checked; unknown data never becomes timeout proof.

`nextEpochTask` selects one bounded freeze, request, capture, allocation, claim, refund or payout from those confirmed accounts. After terminal completion, a new epoch opens only for short-lived explicit sale demand while stock remains; there is no perpetual empty-window rent loop. `requestSaleWindow()` expires after 30 seconds and is consumed by an already open or newly opened window. Host automatic state polling must not continuously renew demand. `buildSigned` constructs the existing program instruction, signs and simulates exact bytes, but never broadcasts. The adapter never fulfills the provider's randomness request itself. Production fulfillment comes from ORAO; a test-only local provider fixture may fulfill on Surfpool.

`backend/src/pack-jobs.ts` mounts this into the existing SQLite connection through `createPackJobStore`. The runner uses a database-backed lease and fencing token, one pending transaction per market, deterministic action keys, and atomic signed checkpoints before the first broadcast. It processes at most the configured batch size and creates no interval. The existing backend scheduler owns its cadence and must rotate/select batches if the configured allowlist exceeds that size.

`recoverOperatorTransaction` checks chain and signature identity. Confirmed/failed signatures reconcile without another broadcast; a still-valid unresolved job can resend only exact saved bytes. Expired absent signatures stay unresolved for on-chain reconciliation, and a definitive failed job requires reviewed retry handling. Missing RPC status is never proof of failure. Neither prepared checkpoints nor signed bytes may be exposed by public APIs.

Local proof covers SQLite restart on every operator tick, lease fencing, a lost response after real broadcast, the complete successful epoch lifecycle, four actual Core claims and creator/IQ payout, and a timeout epoch's full-payment refund. It uses generated identities and an isolated Surfpool chain, not production operator funding or public deployment. Private receipts are outside this package; no private keys or Nubbies source art belong here.

Unused requester funding is swept through the existing opcode 9 only after its provider request permits recovery. The epoch's recorded sponsor receives it; neither the current worker nor collection treasury is substituted. Epoch and requester are read together and the requester must be a non-executable, empty System account. The runner retains the latest confirmed transaction slot and passes it as the next read's minimum context, so a sweep observation is not generated from a bank older than its own confirmed payout. Subsequent genuine requester deposits can be recovered with a distinct observed balance/context identity, while a pending signed sweep always reconciles first. Core rent, the actual provider request cost and network fees are not refunded by this surplus sweep.

For a demand-driven subsequent window, the operator passes the prior requester PDA as part of opcode1's terminal-state proof. When the prior epoch had a provider request, it prepends opcode 9 to the recorded sponsor in the same signed transaction, even when the observed requester balance is zero. Thus a donation arriving after simulation cannot race the zero-balance requirement or strand sponsor funds. A new window requires full creator/IQ payout or complete buyer refunds; an allocated-but-unclaimed or allocated-but-unpaid epoch cannot be skipped.

The native host's optional `pack-window` API does not infer demand from public GETs. It issues a one-use, short-lived message bound to the canonical API origin, chain, program, collection and wallet. Only a valid Wallet Standard message signature can reserve an explicit finite market window budget. A separate allowlist admits frontend request origins without reflecting arbitrary origins into the signed message. The rolling24h cap counts accepted target epochs and prepared/submitted/confirmed open jobs conservatively. Concurrent intents cannot reserve beyond that cap.

Accepted execution intent is retained in the existing SQLite database for up to five minutes, not merely in the process's 30-second demand latch. The host refreshes those approved targets before its existing bounded periodic job pass and triggers one pass on acceptance. A completed epoch advance consumes the target, so restarts or delayed confirmations cannot create perpetual windows. Missing configuration/budget means the demand API is disabled. The wallet signs an intent message, not a transaction and not a commitment to spend its SOL.

Durable accepted window intent is pinned to its program and chain as well as collection/epoch. Restarting with different deployment configuration never replays that approval; legacy rows without pins remain unbound and require operator review. The operator checkpoint database/market namespace itself must also remain isolated per deployment. Keep V4/old-program pending checkpoints in their original namespace until reconciled; never reuse those rows under a new chain/program configuration. These modules do not claim automatic cross-deployment migration of signed transactions.

### Optional native backend bootstrap

`backend/src/pack-runtime.ts` supplies the default-off application adapter. Its explicit configuration pins the incumbent NFT Anchor program, pack program, RPC genesis, gateway, API/frontend origins, provider treasury, separate operator signer, reserve and finite rolling window budget. It reads the existing `collection`/`slot` database and confirmed Core/registry accounts. A successful creator finalization registers its permanent, verified render kit with the sale/state/outfit/operator maps; startup reconstructs the same registrations from finalized rows without retained upload staging. A newly minted Core asset can resolve its collection before the periodic slot reconciler catches up. Invalid/missing permanent material leaves that collection unavailable rather than substituting local art.

History is paginated directly from confirmed chain state: two epochs per page, at most 64 tickets and 256 issuance records, plus up to six currently equipped traits. Epoch-PDA filters keep each issuance query bounded to 128 records. Older activity remains reachable without a whole-collection scan or another indexer, and off-page equipment remains removable. The operator reads only its active epoch and retains its signed demand and daily funding budgets; history size no longer blocks later windows. Immutable metadata/recipes still use the existing IQ gateway cache, while mutable page reads coalesce for one second. HTTP history requests reuse the existing host IP rate limiter. Trusted proxy headers and the host's `RESERVE_PER_IP_PER_MINUTE` policy must be configured for its audience. This is not a zero-RPC or arbitrary-provider performance claim.

The job database is scoped to one reviewed program/cluster deployment. Keep separate SQLite/checkpoint namespaces across deployment changes; never reuse pending old-program jobs under a new program ID. Ordinary HTTP reads do not open windows or spend operator rent. Only the one-use signed window-intent API can request a bounded new window, and the operator rechecks the native history allowance before signing it.
